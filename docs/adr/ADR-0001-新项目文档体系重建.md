# ADR-0001 · 新项目文档体系重建（不沿用旧三层）

- **状态**：`accepted`
- **日期**：2026-11-14
- **决策者**：LIU
- **相关**：[`../../架构总纲.md`](../../架构总纲.md)、[`../README.md`](../README.md)

---

## 背景

从 `D:\Project\xy_project` 的后端（xy-backend）沉淀领域经验，另建纯净版 ERP 与全新 Electron 作品集项目，目标是把整体提升到**架构级开发**，用于求职面试与客户现场展示。

**前端 xy-admin 不参与本项目**：它是 `un-pany/v3-admin-vite` v5.2.0 的业务改造版（2026-11-14 用户明确纠正）。纯净 admin 改为直接拉取上游开源模板重新改造，选型见 [`ADR-0002`](ADR-0002-admin-前端起点选型.md)。

旧项目已有一套成熟的三层文档：`xy_project/项目大纲.md` + 10 篇 `docs/features/*.md`（按功能分区，含流程、涉及文件、🔴 业务红线），其规范是「改任何功能前必读大纲 → 读对应 features 详文 → 分析 → 动手」。

2026-11-14 用户明确指出：该三层是**旧项目的标准，新项目需要重新建立 md**。两者的目标并不相同：

| 维度 | 旧三层 | 新项目需要 |
|---|---|---|
| 视角 | 功能 / 业务流程 | 架构 / 设计取舍 |
| 核心问题 | 改这个功能会踩哪条业务红线 | 为什么这样分层、代价是什么、客户怎么定制 |
| 主要读者 | AI 助手、维护者本人 | 面试官、客户技术方、接手开发者 |
| 组织方式 | 按功能分区（A～E 区） | 按决策、层次、领域、契约 |
| 红线形态 | 🔴 不可违反的业务规则 | ADR 的 Consequences（取舍与代价） |

旧项目的文档体系服务于「**防止改错正在赚钱的业务系统**」；新项目服务于「**证明这是一套想清楚了的系统**」。若直接照搬，简历展示时会出现大量与 ERP 无关的业务细节，反而削弱架构叙事，且会把旧项目的业务耦合带进新仓库。

## 决策

新项目**不建** `项目大纲.md`、**不建** `docs/features/`，改为建立架构级文档体系：

| 文件 / 目录 | 角色 |
|---|---|
| `README.md` | 门面：定位、三产物、隔离声明、快速开始 |
| `架构总纲.md` | **唯一入口**：边界、限界上下文、分层与依赖红线、变更流程、待定决策 |
| `CONTRIBUTING.md` | 工程规范：四关门禁、依赖方向、契约与 ADR 流程、禁止清单 |
| `docs/README.md` | 文档索引与状态口径 |
| `docs/adr/` | 架构决策记录（只增不改，可 supersede） |
| `docs/c4/` `docs/domain/` `docs/contracts/` | 结构图、统一语言与状态机、接口契约 |
| `docs/runbooks/` `docs/showcase/` | 运行手册、演示脚本与讲解话术 |

同时保留旧三层中真正有效的一条机制：**唯一入口 + 改代码前必读**。在 `架构总纲.md` 顶部固化为五步流程，但读的内容从「功能详文与业务红线」换成「分层红线、相关 ADR、契约变更流程」。

旧项目的**领域经验**（金额服务端计算、下单锁库存、状态终态、审计脱敏、生产禁 synchronize、避开 husky stash）以抽象原则形式迁移进 `架构总纲.md` 第 4 节与 `CONTRIBUTING.md`；**业务规则、源码、配置、线上资产一律不迁移**。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A · 架构级文档体系（选定） | 讲得清取舍、可追溯、客户可接手、面试可讲 | 维护成本更高，需要写 ADR 的纪律 | ✅ |
| B · 沿用旧三层、只换内容 | 熟悉、零学习成本 | 仍是功能视角，讲不出架构决策；易夹带旧业务词 | ❌ 否决 |
| C · 两套并存 | 兼顾 | 双份维护、入口不唯一，违背「唯一入口」原则 | ❌ 否决 |
| D · 只写一个 README | 最省事 | 撑不起架构叙事，无决策可追溯性 | ❌ 否决 |
| E · 全英文标准文档（arc42 / C4 全套） | 国际范 | 本人与客户以中文沟通，维护阻力大，易变成摆设 | ❌ 否决（README 与 ADR 标题保留中英关键词即可） |

## 后果

**正面**
- 面试时可直接展示 ADR 与 C4，把「会写代码」升级为「会做决策」
- 客户二次定制有明确边界与依赖红线，接手成本低
- 决策可追溯：任何「为什么不用 X」都有据可查，避免反复争论

**负面 / 代价**
- 每个架构决策都要写 ADR，前期投入增加
- 文档与代码必须同步，契约变更需走流程，短期拖慢速度
- 需要自律：历史 ADR 不可改，否则体系失去意义

## 验收

- [x] 新仓库不存在 `项目大纲.md` 与 `docs/features/` 目录
- [x] `架构总纲.md` 作为唯一入口，含改代码前必读流程与依赖红线
- [x] 存在 ADR 索引、模板与首篇真实决策记录
- [ ] 后续每个架构决策均有对应 ADR，且未出现修改历史 ADR 正文的情况（持续验收）
