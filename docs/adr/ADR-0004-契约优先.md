# ADR-0004 · 契约优先（Zod 为单一真源）

- **状态**：`accepted`（按上轮推荐默认值推进，可随时 supersede）
- **日期**：2026-11-14
- **相关**：[`ADR-0003`](ADR-0003-monorepo与依赖方向.md)、[`../contracts/README.md`](../contracts/README.md)

## 背景

三端都要用同一批 DTO。若后端用 class-validator DTO、前端手写 interface、桌面端再抄一份，任何字段变更都会漂移，且运行时无校验。「契约一致」是本项目第一架构目标。

## 决策

**`packages/contracts` 中的 Zod schema 是唯一真源**：

```
Zod schema  →  z.infer 生成 TS 类型（三端直接 import）
            →  生成 OpenAPI 3.1 文档（对外/给客户）
            →  生成请求校验中间件（erp-api 运行时）
```

- 契约变更顺序：先改 schema → 生成 → 三端同步 → CI 校验，**禁止反向**
- `packages/contracts` 只含 schema 与纯类型，**禁止**任何业务实现或框架依赖
- 错误码、分页、金额等横切结构统一定义在 `schema/common.ts`

## 备选方案

| 方案 | 否决理由 |
|---|---|
| OpenAPI yaml schema-first + 代码生成 | 手写 yaml 易与实现漂移；TS 全栈下 Zod 的运行时校验更直接，OpenAPI 作为产物即可 |
| 后端 DTO 为源导出类型 | 前端与桌面端被后端框架绑定，违反端口适配器 |
| 各端手写类型 | 直接违背「契约一致」目标 |

## 后果

**正面**：改一处三端 typecheck 同时反馈；运行时入参校验免费；客户拿到可读的 OpenAPI 文档。
**负面**：需要维护生成脚本（P1 落地）；schema 设计质量决定全局，前期要慎重。

## 验收

- [ ] `packages/contracts` 无框架依赖，可被纯 Node 脚本生成 OpenAPI
- [ ] 三端无手写重复 DTO（CI 扫描）
- [ ] 生成物与 schema 不一致时 CI 失败
