# 3 分钟演示脚本（面试 / 客户）

> 目标：让对方在 3 分钟内相信「这是一套想清楚了的系统」，而不是「一个后台模板」。

## 0:00 – 0:30 · 定位

> 「这是一套契约优先、外部依赖可替换的通用 ERP 平台，配一个可离线演示的跨平台桌面工作台。我从原有业务系统里抽的是领域经验，不是代码。」

打开 `README.md` → `架构总纲.md`，指第 2 节架构目标表：**每条目标都有可验证方式**。

## 0:30 – 1:10 · 架构决策

打开 `docs/adr/README.md`，讲两篇：

- **ADR-0001**：为什么不沿用旧项目的功能文档，改为 ADR + C4 + 契约的架构文档体系
- **ADR-0002**：为什么选轻量模板而不是 33.8k star 的重量级框架 —— **因为对方自带 monorepo，会盖掉我自己的架构设计**

一句话收口：「选型判据不是功能多少，是能不能讲出自己的决策。」

## 1:10 – 1:50 · 结构证据

打开 `docs/c4/README.md` 与 `docs/design/README.md`：

- 三端共享 `packages/contracts`，Zod 单一真源生成类型与 OpenAPI（ADR-0004）
- 依赖矩阵明确列出 4 条**禁止的反向边**
- 外部能力全是端口 + 适配器，Mock 可直接切（ADR-0005）

## 1:50 – 2:40 · 现场跑通

1. 断网、不开 Docker
2. 桌面端 `demo` 模式启动 → 展示作品集壳 + 项目介绍
3. 切 `live` 模式（或 Web 管理端）→ 跑「登录 → 建商品 → 下单占库存 → 收款 → 履约」
4. 指 `pnpm check` 全绿结果

> 桌面端已落地：`pnpm --filter @erp/desktop build && pnpm --filter @erp/desktop start`。若现场未装 Electron 二进制，用 `pnpm --filter @erp/admin dev` 打开 `/erp/overview` 页替代，两者数据来自同一套契约。

## 2:40 – 3:00 · 收口

> 「这套东西的价值不在功能列表，在于：契约一致、依赖可替换、决策可追溯、现场可复现。客户要换支付或数据库，只写新适配器，不动领域代码。」

## 常见问答

| 问题 | 回答要点 |
|---|---|
| 为什么不用更知名的框架？ | ADR-0002 第 1 条判据：架构自主权 + 面试叙事可读性 |
| 为什么 Zod 而不是手写 OpenAPI？ | ADR-0004：TS 全栈单一真源，OpenAPI 是产物不是源 |
| 演示数据哪来的？ | 全虚构 seed，可重建，与任何真实业务零关联（ADR-0008） |
| 怎么保证不耦合旧业务？ | 禁用词表 + CI 扫描 + 示例模块可整体卸载 |
| 客户端为什么不用现成启动器？ | 旧启动器是游戏代理架构；这里是全新 Electron 三进程 + 安全基线（ADR-0006） |
